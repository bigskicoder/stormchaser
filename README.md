# powder-alert (PART_1)

Storm-signal detection + confidence-scored trip-opportunity alert engine for storm-chasing skiers. Built from `BUILD_PRIMER: powder-alert-platform :: PART_1`.

This is a working, from-scratch implementation — schema, ingestion, scoring engine, alerting, public site, and admin panel — built against **placeholder env vars**. No live Supabase/Clerk/Resend/Vercel/Instagram/Travelpayouts credentials were provisioned in this build session, and outbound network to `api.open-meteo.com` / NRCS's `wcc.sc.egov.usda.gov` was unreachable from the sandbox, so several integration surfaces are built to documented API conventions rather than live-validated. Everything is flagged below and in code comments — search for `ASSUMPTION FLAG` and `VERIFICATION FLAG` in `src/lib`.

## Get running

```bash
npm install
cp .env.example .env.local   # fill in real Supabase/Clerk/Resend/etc keys
```

1. Create a Supabase project, then run the migrations in `supabase/migrations/` in order (`0001_init.sql` through `0006_resort_detail.sql`) via the SQL editor or `supabase db push`.
2. `npm run seed:resorts` — upserts the full US Epic + Ikon resort roster (`src/lib/config/resorts-seed.ts`), then runs the elevation onboarding check, SNOTEL station resolution, and NWS gridpoint resolution against live Open-Meteo/NRCS/NWS APIs.
3. `npm run dev` for local dev, or deploy to Vercel and let `vercel.json`'s cron schedule drive ingestion/scoring/alerts.
4. `npm run test` (vitest — scoring engine unit tests) and `npm run typecheck` before shipping changes.

## What's built (AGENT_DIRECTIVE order)

1. **Schema** — `supabase/migrations/`. Matches BUILD_PRIMER section 4 with RLS added (section 10.5: public read on `resorts`/`snow_scores`/`alerts_fired`, service-role-only writes) and a couple of refinements: `resorts.slr_calibration_multiplier` (section 5.3 calibration hook), `resorts.elevation_check_*` + `snotel_station_*` + `nws_grid_*` (onboarding checks), `accuracy_log` for the backtest loop, and `benchmark_forecasts` for the public-baseline comparison pipeline (section 9 below).
2. **Ingestion** — `src/lib/ingestion/`. Open-Meteo per-model, per-elevation-band pulls (`open-meteo.ts`, `ingest-models.ts`), the elevation onboarding sanity check (`elevation.ts`), SNOTEL ground truth (`snotel.ts`), and Travelpayouts indicative fares (`fares.ts`). Wired to Vercel Cron via `src/app/api/cron/*` + `vercel.json`.
3. **Scoring engine** — `src/lib/scoring/`. Multi-model reconciliation with lead-time-bucketed weights (`reconciliation.ts`), ensemble confidence with the cross-check downgrade (`ensemble-confidence.ts`), swappable SLR strategies (`slr/` — Kuchera default, fixed-ratio baseline, Cobb-Waldstreicher stub), composite powder_score (`powder-score.ts`), a generic wind-hold-probability estimate (`wind-hold.ts`), and the orchestrator (`run.ts`), which computes each resort's scoring day (and its own target-date list) on its own LOCAL timezone rather than UTC (see "Real bugs found by code review" below). All thresholds/weights are named constants in `src/lib/config/constants.ts` — nothing inline. 118 unit tests total across `tests/`.
4. **trip_opportunity contract** — `src/lib/trip-opportunity.ts`, matches section 6 exactly, no internal scoring details leaked.
5. **Alerting** — `src/lib/alerts/` (trigger + 24h rate limit + Resend dispatch), `src/lib/email/`.
6. **Public site** — `src/app/page.tsx` (with an interactive, pan/zoom US resort map — `src/components/resort-map.tsx`), `src/app/resorts/[slug]/page.tsx` (snowfall bar chart spanning past week/today/next 5 days, a conditions strip with weather/wind/SLR/wind-hold visuals, an operator-curated webcam embed, and the full numeric forecast table). No auth wall, per-request rendered (scores change hourly). Designed (ROADMAP Phase D) with a dedicated "alpine night" visual system — see `src/app/globals.css` for the token palette and `src/components/` for the reusable presentational components.
7. **Admin panel** — `src/app/admin/`, Clerk-gated + `ADMIN_USER_IDS` owner allowlist. Generates a social graphic via `@vercel/og` (`src/app/api/admin/graphic/[alertId]/route.tsx`, matching the same visual system as the public site), drafts a caption (`src/lib/social/caption.ts`), and posts to Instagram via the two-call Graph API flow (`src/lib/social/instagram.ts`) only after manual approval (`src/app/api/admin/post/[alertId]/route.ts`).
8. **Backtest/accuracy logging** — `src/lib/backtest/accuracy.ts`, daily cron + a minimal `/admin/backtest` report.
9. **Public-baseline comparison pipeline** — `src/lib/ingestion/nws.ts`. Compares our scoring engine against NWS (`api.weather.gov`) gridded forecasts, both measured against SNOTEL ground truth via the same backtest/accuracy_log pipeline. This is deliberately **not** an OpenSnow integration — see "On OpenSnow" below.
10. **Self-tuning SLR calibration (recommend-only)** — `src/lib/calibration/`. ROADMAP Phase B. A weekly cron proposes a bounded change to a resort's `slr_calibration_multiplier` from its recent `accuracy_log` history; nothing is applied until approved at `/admin/calibration`. See `ROADMAP.md` for the guardrails (min sample size, max step, hard bounds) and why recommend-only is the starting mode. 8 unit tests in `tests/calibration/`.

See `ROADMAP.md` for what comes after PART_1 — operational-readiness steps, current progress against plan, and the prioritized non-coding punch list.

## Flagged assumptions — verify before trusting in production

Status as of the WebSearch-assisted verification pass described in `ROADMAP.md`'s progress log — direct WebFetch to every candidate primary-source domain (open-meteo.com, weather.gov, inscc.utah.edu, pivotalweather.com, wcc.sc.egov.usda.gov) returned `EGRESS_BLOCKED` in this sandbox, so nothing here is a confirmed live response — but WebSearch itself works and surfaced real, independently-converging corrections against two of these, which are now fixed:

- **Kuchera SLR coefficients** (`src/lib/scoring/slr/kuchera.ts`) — **corrected this session.** Two independent WebSearch queries both converged on the same formula from Veals et al. 2025, which has the slope magnitudes swapped from what was originally shipped (published: slope 2 above the 271.16K threshold, slope 1 below it; this codebase originally had -1.0/-2.6, i.e. backwards on both which branch is steeper and by how much). Fixed, with 2 new tests pinning the exact corrected values. Still short of reading the primary-source PDF directly (blocked) — worth doing if this matters enough to you, but meaningfully de-risked from "pure memory recall" to "two independent sources agree."
- **NRCS AWDB REST API** (`src/lib/ingestion/snotel.ts`) — **partially corrected this session.** WebSearch surfaced that this API has no server-side spatial/bounding-box filtering at all (the documented pattern is: fetch the full station list, filter client-side) — the original code's `bBox` param was almost certainly a no-op or an error. Fixed: now fetches the full SNTL network list once and does the nearest-match client-side, which the code was already set up to do downstream anyway. The endpoint path and field names (`/stations`, `WTEQ`, `stationTriplet`) remain unverified against a live response.
- **Open-Meteo request shape** (`src/lib/ingestion/open-meteo.ts`) — **spot-checked this session, looking good.** WebSearch independently confirmed the dedicated model endpoints (`/v1/ecmwf`, `/v1/dwd-icon`, `/v1/gem`), the `/v1/ensemble` endpoint's required `models=` parameter, the elevation parameter's role (90m DEM grid-cell selection), and the specific hourly variable names used (`freezing_level_height`, `temperature_850hPa`, `cloud_cover`, `wind_speed_10m`) — all matched what this code already assumed. Not exhaustively checked (every variable name, the exact ensemble `models=` identifier string like `gfs_seamless`), but the structural assumptions held up.
- **NWS gridded forecast shape** (`src/lib/ingestion/nws.ts`) — unchanged, still only documented-convention-level confidence (higher than the others per NWS's API being older/more stable, but not independently re-checked this session beyond the original build).
- **Travelpayouts fare response shape** (`src/lib/ingestion/fares.ts`) — **corrected this session.** The real response is `{success, data: [...]}` with `data` as a flat array (not nested by destination/flight-key as originally assumed), and the field names differ too: `value` not `price`, `depart_date`/`return_date` not `departure_at`/`return_at`. Fixed. `airline` wasn't confirmed present in the documented response — kept optional/nullable rather than assumed. Low real-world impact either way: section 2.4 already treats this whole enrichment as optional and non-blocking.
- **Instagram Graph API publish flow** (`src/lib/social/instagram.ts`) — **partially corrected this session.** The two-call parameter names (`image_url`, `caption`, `creation_id`) are confirmed correct as originally built. Two things fixed: the hardcoded API version (`v21.0`) was likely close to Meta's ~2-year deprecation window by now — made configurable via `IG_GRAPH_API_VERSION`. There's also a real fork in Meta's current product line between `graph.facebook.com` (the classic Instagram Graph API via a Facebook-connected account — matches the primer's "Tester role"/dev-mode-app description, kept as the default) and `graph.instagram.com` (a newer, separate product). Confirm which one your actual app setup uses via `IG_GRAPH_API_BASE_URL` if needed.
- **NRCS AWDB `/data` endpoint** (`src/lib/ingestion/snotel.ts`) — **corrected this session.** Param names/order (`stationTriplets`, `elements`, `duration`, `beginDate`, `endDate`) confirmed matching. The `duration` value was sent as `"DAILY"` uppercase; documented values are lowercase (`daily`, `hourly`, ...) — fixed.
- **Resend `batch.send` size limit** (`src/lib/alerts/dispatch.ts`) — **real bug, fixed this session.** Confirmed via WebSearch: max 100 emails per batch call. The original code sent one unchunked batch for all matching subscribers — would have hard-failed the moment any single resort passed 100 subscribers. Fixed: chunks into groups of ≤100, sends all chunks even if one fails, tracks actual delivered count.
- **Vercel Cron on the Hobby plan** — see "Known follow-ups" below. Confirmed, not just flagged: Hobby cannot run this project's cron schedule at all.
- **Resort seed data** (`src/lib/config/resorts-seed.ts`): lat/lng/elevation for the full US Epic + Ikon roster (51 resorts) compiled from training knowledge, not a live source. `npm run seed:resorts` runs each one through the Open-Meteo Elevation API onboarding check (section 2.1a) and flags >150m discrepancies — review flagged resorts before trusting their scores. `mid` elevation is a base/summit midpoint interpolation, not a measured mid-mountain figure.
- **SNOTEL station mapping**: resolved via a bounding-box nearest-station search at seed time, not hardcoded — many Northeast/Midwest resorts will legitimately resolve to no station (SNOTEL is a western-US network), so those resorts have no backtest ground truth by design.
- **Column-Tmax simplification** for Kuchera: uses precip-weighted mean of (surface temp, sub-500hPa pressure-level temps) across a day's hourly rows as a single representative Tmax, rather than a full per-timestep SLR-then-sum. Documented in `src/lib/scoring/aggregate.ts` and `run.ts`.
- **Wind-hold-probability estimate** (`src/lib/scoring/wind-hold.ts`) — deliberately generic, not resort-specific. This codebase has no per-resort/per-lift wind-hold threshold data (each resort's own operational policy, not published anywhere this pipeline ingests), so the estimate is a documented logistic curve over forecast wind gust (see the constants' header comment in `src/lib/config/constants.ts`), surfaced in the UI as an estimate, never a guarantee a lift will or won't run.
- **Resort webcams** (`resorts.webcam_url`) — operator-curated, same pattern as `elevation_base_m`/`slr_calibration_multiplier`, not scraped. Requested directly ("pull from resort pages"), but automated scraping of ~40+ different resort sites' webcam pages (different structures, JS-rendered players, real ToS risk per-site) is exactly the kind of scraping-at-scale tradeoff already declined once this session for OpenSnow — see "On OpenSnow" below. Every resort currently has `webcam_url = null` until manually populated; the page renders a "not linked yet" state until then.
- **SNOTEL "snowfall in the past week"** — now computed from day-over-day deltas in raw SNOTEL snow depth (SNWD), clamped at zero (settling/melt isn't negative snowfall), not from the pre-existing WTEQ (snow-water-equivalent) field — WTEQ is cumulative and would conflate settling with melt. See `computeDepthChangeSeries` in `src/lib/ingestion/snotel.ts`. Same western-US-only SNOTEL coverage caveat as the existing ground-truth pipeline applies here too.

The common thread: WebSearch (which goes through Anthropic's own infrastructure, not this sandbox's egress proxy) works even when WebFetch and raw `curl` to the same domains don't. If you want the remaining gaps closed fully, a session with real outbound network access (or you manually checking a couple of URLs) would let this go further than search-engine summaries.

## Real bugs found by code review, not API verification

These weren't WebSearch findings — logic bugs caught by re-reading the pipeline itself. **Both fixed this session, before any live deployment, so no real historical data was ever affected — but either would have been a serious production incident if it had shipped.**

**Alert trigger could re-fire forever on a stale, long-resolved storm — the more severe of the two.** `lib/alerts/trigger.ts` originally queried a resort's entire `snow_scores` history (no `target_date` filter at all) ordered by `powder_score` DESC first, `computed_at` DESC only as a tiebreaker. That finds whichever single row ever scored highest, including a date that's already passed and including a since-superseded forecast for that same date. Combined with the 24h rate limit resetting on its own, this would have **re-sent an alert for the same long-past storm indefinitely, every 24 hours, forever** — not a one-time nuisance but an ongoing credibility problem for the entire alerting feature, undermining the product's own stated transparency/trust positioning. The exact same bug pattern, lower-stakes but still real, existed in the public homepage's "best upcoming score" query (`lib/public/resort-scores.ts`) — it could display a stale, since-corrected score for a date still on the books. Both fixed: filter to `target_date >= today`, dedupe to the *latest* `computed_at` per date first, then pick the best among those current assessments — never let an old score outrank its own later correction. The trigger-side fix is a pure, exported function (`selectCurrentBestQualifyingScore`) specifically so this logic has real unit tests (7 of them, including the exact bug-reproduction scenario) rather than relying on manual inspection.

**Local-day-boundary mismatch.** `lib/scoring/aggregate.ts` and `lib/ingestion/nws.ts` originally computed each "target day"'s hour-range using **UTC midnight**, not the resort's own local midnight. Every seeded resort is in a US timezone 5-8 hours behind UTC, so this silently shifted which hourly `forecast_pulls` rows counted toward "today" by that many hours, for every resort, every day — overnight storms would get misattributed between adjacent ski-days. Fixed with a new dependency-free, `Intl`-based utility (`src/lib/utils/timezone.ts`, `localDateRangeToUtc`/`utcInstantToLocalDateIso`/`localDayBoundsContaining`) and threaded through `lib/scoring/run.ts`, `lib/scoring/aggregate.ts`, and `lib/ingestion/nws.ts` (the NWS benchmark had the identical bug — important since section A.1's whole point is comparing our forecast against NWS's for *the same day*, which wasn't true before this fix). 9 new tests, including the US DST spring-forward/fall-back transition days specifically (23-hour and 25-hour local days), since those are exactly where a naive "add 24h" implementation breaks and this one doesn't.

**Same bug class, found again while building the resort detail page's "today"/"next 5 days" visuals — in two more places.** `lib/scoring/run.ts`'s `nextNDates` generated the scoring orchestrator's entire target-date list from UTC "today," computed once and reused for every resort regardless of timezone — for US resorts (always behind UTC), UTC's calendar date rolls over to "tomorrow" several hours before any US resort's local midnight, so during that multi-hour window (roughly evening through early morning local time, **every single day**), the date list started at local tomorrow and silently skipped generating a score for today's own date. `lib/public/resort-scores.ts`'s `getUpcomingScoresForResort` had the identical root cause on the read side — `target_date >= today` compared against a UTC "today" that could already be tomorrow, excluding today's own row from "upcoming" during that same window. Both fixed the same way as the original instance: resolve "today" from the resort's own timezone (`localTodayIso`), not `new Date().toISOString()`. 3 + reused coverage in existing suites; see `tests/scoring/run.test.ts` for a test that reproduces the exact Eastern-vs-Pacific-vs-UTC discrepancy at one fixed instant.


## On OpenSnow

The operator asked about comparing against OpenSnow directly. We're not doing that — see `ROADMAP.md` for the full reasoning, but short version: OpenSnow is a paid, proprietary consumer product with no public API and a ToS that doesn't permit automated access, even for paying subscribers. The BUILD_PRIMER already drew this line in section 2.3 ("do not scrape, do not reference their scoring methodology"). Instead, the public-baseline comparison pipeline (`src/lib/ingestion/nws.ts`) builds the same *kind* of comparison — "is our forecast better than a baseline" — against NWS's public-domain gridded data, which answers a more defensible question (are we beating a plain public forecast) without touching anyone's proprietary product. A manual, human-entered comparison log against OpenSnow (you read their number yourself, we store it) remains a legitimate option if wanted later — not built yet, no ToS issue since there's no automated access involved.

## Known follow-ups (not blocking, not built)

- **Cron cadence vs. Vercel plan tier — resolved, action required.** `vercel.json` schedules 10 jobs at hourly/6h/daily/weekly cadence. WebSearch confirmed (2026): Vercel's Hobby (free) tier allows at most 2 active cron jobs, each capped at once-per-day. This project's design needs **Vercel Pro ($20/mo)**, not Hobby — this isn't a "maybe," the current `vercel.json` simply won't deploy as-is on Hobby. Budget for this in Phase 0 (see `ROADMAP.md`).
- **Open-Meteo commercial tier**: currently on the free non-commercial tier per section 2.1. Required once the product is monetized — `OPEN_METEO_API_KEY` is already wired as an env var for when that switch happens.
- **`npm audit` — two critical RCEs patched this session.** Between the original build (2026-08-22) and this update (2026-10-04), two **critical, unauthenticated remote-code-execution** advisories landed against Next.js itself (Windows-hosted servers; the AVIF image-optimization path). `npm audit fix` (non-breaking — stayed within the `^15.1.4` range, landed on `15.5.27`) resolved both; verified clean build/typecheck/tests after. Remaining: 12 lower-severity advisories, mostly transitive through build tooling (`postcss`/`sharp` need Next 16, a breaking change, to fully clear — deferred, same reasoning as before) and one *critical* advisory in `vitest`'s UI-server feature specifically, which this project doesn't use (`package.json` only ever runs `vitest run`, never `vitest --ui`) — real-world risk here is close to zero despite the severity label, but worth a `vitest@5` bump eventually. Run `npm audit` yourself periodically; this class of finding changes over time, not just at initial build.
- **Admin 403 status code**: an unauthorized `/admin` visitor sees a 403 message but the HTTP response is a 200 (Next.js Server Components don't set a custom status without the `forbidden()`/`unauthorized()` APIs). Access is genuinely blocked either way; only the status code is cosmetically wrong.
- **Cobb-Waldstreicher SLR strategy**: documented stub only (`src/lib/scoring/slr/cobb-waldstreicher.stub.ts`), per section 5.3 — needs vertical-motion/RH ingestion this pipeline doesn't pull yet.
- **Seasonal pattern modeling (ENSO)**: documented stub only (`src/lib/scoring/seasonal-pattern.stub.ts`), per section 1's explicit "stub a placeholder module, do not implement logic" directive — this was missing until a full primer audit caught it (see `ROADMAP.md`).
- **Section 9 resort shortlist**: seeded with the full US Epic + Ikon roster per operator direction (superseding the primer's own SLC-placeholder fallback). Resort list is fully DB-editable — see section 9 / `resorts` table, never hardcoded elsewhere.

## Architecture notes

- Single Next.js app (App Router) rather than a separate Express service: Vercel Cron needs plain HTTP GET targets, which Next Route Handlers serve directly (`src/app/api/cron/*`). The Express 5 reuse the primer calls for (section 3) lives at `src/server/express-app.ts`, mounted into Next via a `node-mocks-http`-based adapter (`src/server/node-adapter.ts`) at `/api/express/*` — used for the subscribe endpoint and the read-only trip-opportunities lookup, the two places that genuinely fit Express's middleware-and-router shape. Local dev + curl end-to-end tested; see comments in `node-adapter.ts` and `express-app.ts` for two real bugs hit and fixed along the way (node-mocks-http's default no-op EventEmitter stub, and `finalhandler`'s `req.unpipe()` crash on a non-stream mock request).
- Both SLR strategy and multi-model reconciliation are swappable via clean interfaces (`src/lib/scoring/slr/types.ts`, `src/lib/scoring/reconciliation.ts`) per section 10, non-negotiable principle 2.
- No booking-partner SDK, auth, or data model anywhere in the codebase — the `trip_opportunity` payload (section 6) is the only surface a future PART_2 booking layer would touch.
